# 🏗️ Архитектура ядра ShadowGram

Архитектура системы ShadowGram построена по модульному принципу с четким разделением ответственности между менеджерами ресурсов (`src/core/managers`), модулями автоматизации (`src/core/base_module.py`) и графическим интерфейсом на PyQt6 (`src/ui`).

```
┌─────────────────────────────────────────────────────────────┐
│                    PyQt6 UI Layer                           │
│  (MainWindow, ListPage, NodeEditor, Services, Settings)     │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│                  Core Managers Layer                        │
│ ┌───────────────────┐ ┌──────────────────┐ ┌──────────────┐ │
│ │  AccountManager   │ │   FarmManager    │ │ConfigManager │ │
│ └───────────────────┘ └──────────────────┘ └──────────────┘ │
│ ┌───────────────────┐ ┌──────────────────┐ ┌──────────────┐ │
│ │  ProcessManager   │ │   ProxyManager   │ │  HwManager   │ │
│ └───────────────────┘ └──────────────────┘ └──────────────┘ │
└──────────────────────────────┬──────────────────────────────┘
                               │
               ┌───────────────┴───────────────┐
               ▼                               ▼
┌─────────────────────────────┐ ┌─────────────────────────────┐
│   Desktop Client Sandbox    │ │   Headless MTProto Engine   │

└─────────────────────────────┘ └─────────────────────────────┘
```

## 1. Менеджеры ядра (`src/core/managers/`)

### `config_manager.py`
- Управляет чтением и атомарной записью `config.json`.
- Реализует потокобезопасный доступ (`threading.Lock`) и кэширование по `mtime` файла.
- В случае повреждения JSON автоматически восстанавливает конфиг из `config.json.bak`.

### `farm_manager.py`
- Отвечает за изоляцию ферм: создание, переключение и удаление ферм из папки `farms/`.
- Синхронизирует текущую активную ферму через файл `active_farm.txt`.
- Переключает рабочие каталоги аккаунтов и пути к сессиям при смене активной фермы.

### `account_manager.py`
- CRUD операции над аккаунтами внутри активной конфигурации.
- Проверка структуры директории аккаунта (`.session`, `tdata`, аватары).
- Экспорт сессий для серверного использования (`pack_selected_sessions`).

### `process_manager.py`
- Запуск и мониторинг нативных процессов Telegram Desktop.
- Определение доступности утилит песочницы: `shutil.which("bwrap")` или `firejail`.
- Проброс переменных окружения, сокетов X11/Wayland и изоляция файловой системы.

### `proxy_manager.py`
- Валидация HTTP/SOCKS5 прокси.
- Генерация конфигурационных файлов `proxychains.conf` для аккаунтов.
- Поднятие локального туннеля через бинарник `gost` (v3) с динамическим выделением свободных портов.

### `hw_manager.py`
- Генерация и кэширование аппаратных профилей (Fingerprints).
- Формирование фиктивных DMI данных: производитель (`sys_vendor`), модель материнской платы/ноутбука (`product_name`), серийные номера и BIOS.

## 2. Изоляция и маскировка процессов (Sandbox & Stealth)

При включении Stealth-режима запуск Telegram Desktop осуществляется через песочницу `bubblewrap` (`bwrap`):

```bash
bwrap \
  --dev-bind / / \
  --ro-bind-data <fd1> /sys/devices/virtual/dmi/id/sys_vendor \
  --ro-bind-data <fd2> /sys/devices/virtual/dmi/id/product_name \
  --bind /tmp/.X11-unix /tmp/.X11-unix \
  --ro-bind <zoneinfo_file> <target_localtime> \
  --unshare-uts --hostname <device_model> \
  proxychains4 -f <proxychains.conf> \
  /usr/bin/Telegram -workdir <account_dir>
```

### Ключевые моменты реализации:
1. **Подмена DMI:** Данные передаются через файловые дескрипторы виртуальных пайпов (`os.pipe()`), исключая запись временных файлов на диск.
2. **Разрешение симлинка `/etc/localtime`:** Чтобы избежать ошибки `Can't mount on symlink destination`, система определяет реальный целевой файл через `Path("/etc/localtime").resolve()` и монтирует файл часового пояса поверх него.
3. **Изоляция сети:** Запуск через `proxychains4` гарантирует, что Telegram не выполнит прямых запросов в обход назначенного прокси.

## 3. MTProto Слой (Hydrogram & Сценарии)

Для задач автоматизации, не требующих графического интерфейса Telegram, используется клиент на базе **Hydrogram**:
- Подключение с сессионным файлом `.session` (SQLite формат).
- Поддержка проксирования напрямую через PySocks/SOCKS5 либо через локальный Gost туннель.
- Обработка `FloodWait` с экспоненциальным бэкоффом.
- Выполнение логики через `NodeScenarioExecutor` и наследников `BaseModule`.
